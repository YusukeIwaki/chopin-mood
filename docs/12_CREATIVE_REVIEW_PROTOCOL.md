# 12 — 制作と独立レビューの決定規約

目的は、本人の演奏が主役の、素朴で見続ける理由のある短編を継続して作ること。意見を戦わせるのは、作品の弱点を実物から発見するためであり、反対意見の数を増やすためではない。

人がIssueに録音と希望を書き、Codexへ制作を依頼する。Codexは最大3案をローカルで制作・検証して候補ごとにPRを出す。PRコメントの修正も明示的な依頼を受けて同じPRで行う。ownerが1案をMergeすると、その成果物を検証してReleaseし、元Issueと競合するPRを閉じる。具体的なActionsと証拠の契約は[運用手順](10_GITHUB_STUDIO_OPERATIONS.md)、コマンドは[開発ガイド](../scripts/README.md)を参照する。

## 役割と権限

| 役割 | 守るもの・反論する相手 | 決定できること |
| --- | --- | --- |
| 制作担当 | ownerの希望を実装する。数値変更だけでは直らない描画の問題を引き受ける | 企画、素材、構図、描画、修正案 |
| 音楽・同期レビュアー | 演奏の時間と聴こえ方。視覚的な派手さが音楽を壊す案へ反論する | 実測と聴取範囲に基づく指摘。同期の閾値変更は不可 |
| 画面・視聴レビュアー | 読める形、連続した動き、見続ける理由。「素朴」で単調さや未完成を隠す案へ反論する | 実画像・動きに基づく指摘。未確認の聴感は判断しない |
| 編集責任者 | 希望・音楽・画面・継続制作の負担の釣り合い | 好みの対立の裁定、修正の優先順位、候補を提示するか停止するか |
| owner | 最終的に公開する作品の選択 | コメントで希望を追加し、選んだPRをMergeする |

制作を統括するCodexが編集責任者も担う。レビューは制作と独立した2つのサブエージェントの文脈で行い、実物と希望を渡す。制作側の期待する結論は渡さない。サブエージェントが使えない場合は独立したレビュー用セッションを使い、それも不可能なら未検証と報告する。自己採点を独立レビューと記録しない。

入口は[studio-produce](../.agents/skills/studio-produce/SKILL.md)、各レビューは[studio-review](../.agents/skills/studio-review/SKILL.md)、裁定は[studio-arbitrate](../.agents/skills/studio-arbitrate/SKILL.md)。レビュー役はソース・映像を書き換えず、GitHubへの投稿やMergeも行わない。

## 対立させる問い

- **静けさと退屈**: 長く保つ構図に、注目する対象や小さな変化があるか。動きを増やす提案は、演奏より前に出ないか。
- **同期と自然さ**: 指定フレームに効果が出ても、強調する音の選択は妥当か。聴取できていない部分を数値で埋め合わせていないか。
- **一貫性と反復**: 同じ人物・空間は作品のまとまりを助けるか。近作と同じ構図・モチーフを無意識に再生産していないか。
- **魅力と制作負担**: 素材の作り直しが体験を改善するか。既存の素材や小さな描画修正で同じ問題を直せないか。

すべての作品に人物、物語、月、回想、大きなカメラ移動を要求しない。抽象表現も成立しうる。逆に、色替えだけを意味のある展開と説明して済ませない。各作品で「何を見続けてもらうのか」を実物で示す。

## 証拠と判定

新規候補は `studio/projects/issue-N/candidates/cand-01/` 〜 `cand-03/` に保存する。`editorial.json` は編集判断の記録であり、[candidate_project.py](../studio/candidate_project.py) の `validate_editorial` と `editorial_template` が形式の契約である。[studio_candidate.py](../scripts/studio_candidate.py) の `render` が未レビューのテンプレートを作り、独立した評価を埋めた後に `validate` で実物との一致を確認する。音源、モデルの非公開ログ、Secretは含めない。各レビューに以下の内容を記録する。

- `input_sha256` は `project.json`、`brief.json`、`storyboard.json` の実バイトのハッシュ、`media_sha256` は `video.mp4`、`contact-sheet.jpg`、`timeline.html` のハッシュ。`qa_sha256` と `qa` も現在の結果へ結び付ける。
- `reviews.music` と `reviews.visual` は別セッションの `reviewer_id` を持ち、どちらも `creator_id` と異なる。入力・メディア・QAから決まる同じ `evidence_sha256` を返す。識別子を書いただけでは独立実行の証明にならないため、実際の委任と証拠確認も必要。
- 各レビューは `verdict`、`hard_blockers`、ID付きの `concerns`、実際に見たものを示す `evidence`、`listening`、`limitations` を持つ。成立する点と懸念の具体的な観測・影響・改善を証拠と懸念の記述に含める。
- `decision` は `editor_id`、`verdict`、`rationale`、役割と懸念IDで結び付く `resolutions` を持つ。`accept` は懸念を認めた上でその表現を採用する判断、`fixed` は実物で修正を確認した判断。どちらも機械的な不合格の免除には使わない。

追加希望の取得内容は `studio_candidate.py feedback` でgit管理外の `output/studio/issue-N/feedback-pr-N-request-R.json` に保存する。PR本文へコメントID・URL・取得時点・対応・再検証の表を残し、今回の依頼に対する `round` の開始根拠も記す。旧版の不合格や裁定はGit履歴・Actionsの証跡とコメントに残す。候補の4ファイルへ独自のキーや完全なコメント列を追加しない。`round` は依頼ごとの0〜2を検査するが、過去の依頼との連続性を自動で証明するものではなく、Git履歴とPRで確認する。

本編の「機械的同期」、音声の「音楽的判断」、画面の「美的判断」を別々に扱う。コンタクトシートは静止画の証拠であり、連続した動きの証拠にはならない。短いプレビューの合格も全編の動作確認へ一般化しない。音楽担当が聴取しなかった場合は `listening: unavailable` と具体的な `limitations` を残し、音楽的合格を宣言しない。聴取未実施だけではPR提示を妨げず、機械QAの合格を取り消さない。その限界をPRに表示し、音楽的自然さの未確認を合格へ読み替えない。

| 指摘の種類 | 例 | 決着 |
| --- | --- | --- |
| 阻害要因 | 符号化後の同期失敗、音源の不一致、owner制約違反、読めない主役、必須ゲート不合格 | 実物で修正確認するまで合格不可 |
| 表現上の選択 | 同じ余白を心地よい／長いと感じる、寒色／暖色の好み | 編集責任者が狙いと証拠から選び、反対理由も残す |
| 未確認 | 動きの実物がない、必要なハッシュがない、聴取できない | 必須の証拠なら保留。任意の評価なら限界として明示 |

指摘はフレーム・ファイル・音声の聴取範囲などへ結び付ける。根拠のない「つまらない」「音楽に合わない」を阻害要因にしない。好みを事実に言い換えて拒否権を得ることも、事実を好みに言い換えて通すことも認めない。点数を平均して重大な失敗を相殺しない。

## 修正の上限と最終決定

1. 制作担当が初回版を作り、2役が独立に確認する。初期の静止画・動き確認で見つけた問題は、本編へ先送りせず早く直す。
2. 編集責任者は両者の指摘を一度に読み、阻害要因と重要な改善に絞った修正指示を出す。表現上の選択は、ownerの希望 → 演奏への注意 → 素朴さと持続性 → 制作負担の順に判断する。
3. **候補ごとに初回＋実質的な修正2回まで**。各修正の後、変更した実物を再評価する。静止画段階と本編段階で別々に2回を与えず、同じ制作依頼の候補で共有する。環境障害の再実行は創作の1回と混同しないが、原因不明の再実行を続けない。
4. 新しい証拠なく閉じた論点を再提案しない。新しい問題は隠さず追加するが、それを理由に上限をリセットしない。別candidateや別セッションへ番号を替えて延長しない。
5. 上限までに合格した案だけを提示する。1案でも十分。残る案は未達として止め、理由と残る改善を記録する。全案が未達なら、合格PRがないことを明示する。基準の引下げ、古い映像の合格の流用、無関係な子Issueへの逃がしはしない。

editorialの裁定はActionsの必須ゲートを置き換えない。自動レビューが不合格なら、好みの裁定だけで成功へ書き換えない。証拠の誤読と考える場合も、同じ上限内で実物を再確認し、根拠を残す。ownerの希望や権利・費用に未解決の選択がある場合だけ、人に具体的な判断を求める。

## コメント改訂と採用

人から「PR #104 のコメントに対応」と依頼された時点の未対応希望を固定する。コメント追加だけでは制作モデルを起動しない。希望ごとの対応と検証を記録し、同じcandidate・同じPRを更新する。新しい明示依頼には初回改訂＋修正2回の予算を与えるが、前の不合格と履歴を消さない。

動画・素材・storyboard・制作コードが変われば、入力とheadに結び付く証跡を更新する。PRの本文だけ更新して古い動画を完成品として出さない。明示的な希望の変更で音楽区間を選び直す必要がある場合も、自動選定を実行し、新しい計画と変更理由を記録する。人間に秒指定やタイムライン修正を頼まない。

ownerによるMergeが1案の採用となる。Releaseの検証成功前に元Issueや他候補を閉じない。Release失敗では採用したPRと証拠を保持して再実行し、別案へ自動ですり替えない。PR本文に `Fixes #元Issue` のような自動close指定を入れない。複数候補の競合や再実行の扱いはReleaseの実装契約に従う。

## 持続的な改善

制作時間、実質修正回数、モデル呼び出し・生成費用の分かる範囲、採用／未達の理由を候補の記録に残す。未測定を0として書かない。次回は実際に頻出した問題だけを手順・描画・素材へ還元し、単発の好みを全作品の規則へ昇格させない。過去作品を比較できない場合はその旨を残し、多様性を確認済みとしない。
